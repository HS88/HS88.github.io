Designing Launch Dimensions: Grid, Block, and Tile Size from the Hardware Up

"Occupancy is not a goal — it's a budget. The chip gives you a fixed number of threads, warps, blocks, and bytes per SM. Your job is to spend that budget so no resource is wasted and no resource is overbooked."
— The engineer's view of CUDA tuning

In the earlier chapters you saw what grid-stride and tiling do, and we hand-traced one combined example on a specific GPU. But every time you write a new kernel, you have to decide three numbers:

  1. How many threads per block?
  2. How many blocks in the grid?
  3. If the kernel tiles shared memory, how big is the TILE?

Pick them wrong and the chip sits half-idle, or your kernel refuses to launch because the shared memory doesn't fit. Pick them well and you get latency hiding, memory coalescing, and enough parallelism that the GPU's schedulers never run out of work.

This chapter gives you a repeatable, hardware-first process for picking all three. By the end you'll have a step-by-step recipe you can run by hand, a cheat sheet for common GPUs, and an interactive calculator that does the arithmetic for you.

The one sentence to remember:
Pick block size first (multiple of 32, shaped like your data). Then size the tile so shared memory lets at least 2 blocks live per SM. Then verify occupancy. Then launch 2–4× as many blocks as the chip can hold at once, and let grid-stride handle the rest.

1. The Mental Model: Four Limits, One Tightest Winner

Before any formulas, hold this picture in your head. Every block you launch is a tenant trying to move into a Streaming Multiprocessor (SM). The SM is the landlord. The landlord has four independent rules:

  1. Block size itself cannot exceed the architecture's max threads per block (512 on GT200, 1024 on everything modern).
  2. Resident threads on an SM cannot exceed maxThreadsPerSM (= blocksPerSM × threadsPerBlock).
  3. Resident shared memory on an SM cannot exceed sharedMemPerSM (= blocksPerSM × sharedMemPerBlock).
  4. Number of resident blocks cannot exceed the architectural cap (8 on GT200, 16–32 on modern).

There is a fifth limit — registers per SM — but we'll defer it to Step 3, because the compiler reports register usage and you usually don't choose it directly.

Key concept: the tightest limit always wins
Each of the four rules gives you an upper bound on "blocks per SM that can fit." Compute all four. The smallest one is your actual blocksPerSM. If the smallest is 1, you have almost no latency hiding and you should back off some dimension. If the smallest is 4+, you're in a good place.
Scenario for Figure 1.1
GT200 (maxBPSM=8, maxTPSM=1024, shared/SM=16 KB=16384 B, regs/SM=16384) running a tiled matmul kernel with TILE=16 (so 256 threads per block, 2 KB shared per block) but 24 registers per thread (a register-heavy variant with extra accumulators). Every bar below is computed from exactly these inputs.
Figure 1.1 — four independent limits on blocks per SM for the stated scenario. The architectural cap (8) and shared-memory limit (8) are both generous; the thread limit allows 4; but the register budget only fits 2 blocks. The smallest wins, so the register limit is binding and you get 50% occupancy — half of what the chip could support if the kernel used fewer registers per thread.

Why GT200 feels so tight
Notice how much smaller GT200's budget is: 16 KB of shared per SM instead of 164 KB, 512 threads per block instead of 1024, 8 blocks per SM instead of 32. Modern GPUs are not just faster — they have an order of magnitude more "room" on each SM, which is why TILE=32 became the default and why newer kernels don't sweat about shared memory.

3. Step 1 — Pick Threads Per Block

This is the first decision, and it almost picks itself. Three rules narrow the field to a handful of choices:

  1. Must be a multiple of 32 (the warp size). A warp is the actual scheduling unit on a GPU; any thread count not divisible by 32 leaves lanes idle in the last warp. 100 threads wastes 28 lanes. 128 does not.
  2. Should match the shape of your data access. For matmul (or any 2D stencil), square: TILE × TILE. For 1D element-wise kernels, flat: 128, 256, or 512.
  3. Shouldn't be max. If you pick maxThreadsPerBlock (e.g. 1024), only one or two blocks can live per SM, which starves the scheduler. Smaller blocks (256 or 512) usually let 4–8 blocks per SM, which is better for latency hiding.
Default to start with
For 2D kernels: TILE = 16 ⇒ 256 threads per block.
For 1D kernels: 256 threads per block.
These give you the right balance of per-block parallelism and room for many blocks per SM on nearly every architecture from Fermi through Hopper.

Why not 128? It works, but with only 4 warps per block, a single stalled warp is a bigger fraction of your block's progress. Why not 1024? Only 1 or 2 blocks per SM, almost no latency hiding. 256 is the sweet spot.

4. Step 2 — Pick TILE from the Shared Memory Budget

Now you decide the tile size. For the standard matmul pattern we've been using, each block holds two tiles in shared memory: As[TILE][TILE] and Bs[TILE][TILE]. In bytes, for float (4 bytes each): 

sharedBytesPerBlock = 2 × TILE² × 4

You want at least 2 (ideally 4+) blocks resident per SM, so that while one block is stalled on a global memory load, another block's warps keep the ALUs busy. Rearranging: 

TILE²  ≤  shrPSM / (8 × desiredBlocksPerSM)
TILE   ≤  sqrt( shrPSM / (8 × desiredBlocksPerSM) )

Worked for a few cases, wanting 4 blocks per SM:

GPUshrPSMBudget per blockMax TILETypical pick
GT20016 KB4 KB2216
GTX 108096 KB24 KB5432
A100164 KB41 KB7132
H100228 KB57 KB8432 or 64
Why not just pick the maximum TILE?
Three reasons. First, TILE must be a multiple of the warp dimension (so TILE×TILE is a multiple of 32), which already rules out most values. Second, a bigger tile means a bigger block (TILE×TILE threads), which quickly runs into the thread-per-SM limit and cuts blocks per SM. Third, powers of two (16, 32) align with coalesced memory access patterns and bank-conflict-free shared access; 22 does not. So in practice TILE ∈ {8, 16, 32, 64} almost always.

5. Step 3 — Verify Occupancy (Who Wins the Tightest Limit?)

Now you compute the real blocks-per-SM. Plug your choices into all four limit formulas and take the minimum: 

blocksPerSM = min(
    maxBPSM,                            // architectural cap
    maxTPSM / threadsPerBlock,          // thread-count limit
    shrPSM  / sharedPerBlock,           // shared memory limit
    regsPerSM / (regsPerThread * threadsPerBlock)   // register limit
)

occupancy = (blocksPerSM * threadsPerBlock) / maxTPSM

Let's walk through A100 with TILE=16, 256 threads/block:

LimitFormulaValueBlocks/SM allowed
Architectural cap—3232
Thread limit2048 / 256—8
Shared memory limit164 KB / 2 KB—82
Register limit (assume 32/thread)65536 / (32×256)—8
← tightest (wins)min—8

Occupancy = 8 × 256 / 2048 = 100%. Beautiful.

Now the same with TILE=32, 1024 threads/block:

LimitFormulaBlocks/SM allowed
Architectural cap—32
Thread limit2048 / 10242
Shared memory limit164 KB / 8 KB20
← tightest (wins)min2

Occupancy = 2 × 1024 / 2048 = 100% as well. But only 2 blocks per SM — much less latency hiding. If one block stalls, only one other is available to step in. TILE=16 gives 8 blocks per SM: when one stalls, seven others take over. For memory-bound kernels on A100, TILE=16 is usually better for this reason.

Rule of thumb
Prefer configurations that give you at least 4 blocks per SM. 2 is okay. 1 is dangerous. Below 50% occupancy, latency hiding breaks down and your kernel becomes bandwidth-starved.

6. Step 4 — Pick the Launch Grid

Now you know how many blocks fit on the chip at any instant: 

concurrentBlocks = numSMs × blocksPerSM

For TILE=16 on an A100: 108 × 8 = 864 blocks can run simultaneously. For TILE=16 on GT200: 30 × 4 = 120 blocks.

6.1 Launched ≠ Resident: the Scheduler Does the Queueing

Before we continue, a point that trips up almost every CUDA learner: the grid size you pass to <<<grid, block>>> is not the same as what runs on the chip at once. The hardware limit (concurrentBlocks) only bounds how many blocks are resident on the SMs at any instant. The grid size is just a logical queue of work — the scheduler drains it in waves.

ConceptWhat bounds itTypical value
Resident blocks
(executing on SMs right now)		 the four limits from Step 3 e.g. 864 on A100
Launched blocks
(what you put in gridDim)		 ~2 billion (gridDim.x max = 231−1) anything you want

So when the recipe says "launch 2–4× concurrentBlocks," that is not a limit violation. You are telling the scheduler: "here are twice as many blocks as the chip can hold — serve them in two waves." The first wave fills the SMs; as blocks finish, the scheduler backfills from wave two until the queue is empty.

Figure 6.1 — launching 1728 blocks on an A100 that holds 864 resident is perfectly legal. The scheduler runs them in two back-to-back waves. You can launch 65,536 blocks (76 waves) just as safely — the hardware limit is on resident, not launched.

6.2 So Why 2–4×? Why Not Exactly 1×? Why Not 100×?

Given that any grid size is legal, the real question is: what size makes the kernel fastest? Three forces are in tension.

Why not exactly 1× concurrent? Because blocks don't all finish at the same time. Some output tiles sit near the matrix edge and do less work (padded zeros); some SMs run faster than others due to cache warmth; some blocks stall on memory for longer than their neighbors. If the grid is exactly one wave, a few slow blocks at the "tail" leave most SMs idle while the chip waits for them to finish.

Figure 6.2 — when the grid exactly fills the chip, uneven block finish times create idle gaps (red hatching). Launching extra blocks lets the scheduler backfill those gaps.

Why not 100× concurrent? Because with that many small blocks, each block does only one output tile and you lose the amortization that grid-stride buys you. Compare:

Launch sizeBlocks each SM processesWork per blockTrade-off
1× concurrent (864 on A100) 1 big (many tiles via stride) tail idle; chip under-utilized
2–4× concurrent (1728–3456) 2–4 medium backfill always ready, overhead amortized
10× concurrent 10 small diminishing returns
= outputTiles (76× for 4K matmul) ~76 one tile each startup/teardown cost paid 76× more often

Each block has non-trivial fixed cost: register allocation, shared-memory initialization, the final __syncthreads() + stores + cleanup. With grid-stride, that cost is amortized over many output tiles. At 2–4× concurrent, you get both benefits: the scheduler always has backfill to hide tail imbalance, and each block still does enough work for amortization to matter.

The core insight
The hardware limit bounds what's resident. The launch count bounds how much work you queue. Grid-stride lets you decouple the two, so each block does a meaningful slab of work instead of one tiny tile.

6.3 Back to the Decision Rule

Now compare to how many output tiles your problem has. For an M×N output matrix: 

outputTiles = ceil(M / TILE) × ceil(N / TILE)

Three cases decide the grid:

CaseGrid to launchWhy
outputTiles ≤ concurrentBlocks launch outputTiles blocks problem is tiny; no grid-stride needed
outputTiles up to ~8× concurrent launch outputTiles blocks chip chews through in a few waves; stride loop not necessary
outputTiles >> concurrentBlocks launch 2–4× concurrentBlocks, use grid-stride decouple grid size from data size; let each block iterate
Analogy: hiring for a shift
If you have 100 tasks and 10 workers, you don't hire 100 temps. You hire ~20 (so each handles 5 tasks with some overlap for breaks) and let them loop through the queue. Launching too few blocks starves the chip; launching exactly as many as you have tasks works until the number of tasks explodes. Grid-stride lets you decouple "how many workers" from "how many tasks."

8. Worked Example: GT200 for 4096×4096 Matmul

Let's walk the process by hand for a historical GPU, where the constraints bite hard.

Step 0 — hardware: 30 SMs, maxTPB=512, maxTPSM=1024, maxBPSM=8, shared=16 KB.

Step 1 — block size: try TILE=16 ⇒ 256 threads/block. That's under GT200's 512 ceiling. Good.

Step 2 — shared memory: 2 tiles × 16² × 4 B = 2 KB/block.

Step 3 — four limits (assume a lean tiled kernel at ~16 regs/thread):

LimitValue
architectural cap8
threads: 1024/2564
shared: 16KB/2KB8
regs: 16384/(16×256)4
← tightest4

Occupancy = 4 × 256 / 1024 = 100%. Excellent — thread and register limits both pin us at 4 blocks per SM.

Step 4 — launch grid:

  • Concurrent on chip = 30 × 4 = 120 blocks
  • Output tiles = (4096/16)² = 256² = 65,536 tiles
  • Ratio = 65,536 / 120 = 546× oversubscription ⇒ use grid-stride
  • Launch ~2× concurrent = 240 blocks, arranged as e.g. dim3(16, 15)
  • Each block handles ~273 output tiles via the grid-stride loop
dim3 block(16, 16);          // 256 threads, TILE×TILE
dim3 grid(16, 15);           // 240 blocks ~= 2 × concurrent
matMulTiledStrided<<<grid, block>>>(A, B, C, 4096, 4096, 4096);

9. Worked Example: A100 for the Same

Step 0 — hardware: 108 SMs, maxTPB=1024, maxTPSM=2048, maxBPSM=32, shared=164 KB.

Step 1 — block size: try TILE=16 ⇒ 256 threads/block.

Step 2 — shared memory: 2 × 256 × 4 = 2 KB/block.

Step 3 — four limits (assume a lean tiled kernel at ~32 regs/thread):

LimitValue
architectural cap32
threads: 2048/2568
shared: 164KB/2KB82
regs: 65536/(32×256)8
← tightest8

Occupancy = 8 × 256 / 2048 = 100%. Thread and register limits tie at 8. A100 has 108 SMs vs. GT200's 30, so the same per-block picture multiplies to much more throughput.

Step 4 — launch grid:

  • Concurrent on chip = 108 × 8 = 864 blocks
  • Output tiles = 65,536
  • Ratio = 65,536 / 864 = 76× ⇒ use grid-stride
  • Launch ~2× concurrent ≈ 1,728 blocks, arranged dim3(48, 36)
  • Each block handles ~38 output tiles via grid-stride
dim3 block(16, 16);
dim3 grid(48, 36);           // 1728 blocks ~= 2 × concurrent
matMulTiledStrided<<<grid, block>>>(A, B, C, 4096, 4096, 4096);
Same kernel, two GPUs, only the grid changes
Notice: the kernel code is identical. The block shape is identical. The only thing that changes is the grid size, driven by hardware capacity. That's the whole point of the grid-stride pattern — you tune the grid to the chip, not to the data.

11. The Escape Hatch: cudaOccupancyMaxPotentialBlockSize

When you don't want to work through the four limits by hand, CUDA has an API that does it for you. Given your kernel's compiled register and shared-memory usage, it picks a block size that maximizes occupancy: 

int minGridSize;      // smallest grid for full occupancy
int bestBlockSize;    // ideal threads per block for this kernel
cudaOccupancyMaxPotentialBlockSize(
    &minGridSize,
    &bestBlockSize,
    matMulTiledStrided,     // your kernel function pointer
    0,                      // dynamic shared mem per block (0 if static)
    0);                     // block size limit (0 = no limit)

// Now launch:
myKernel<<<minGridSize, bestBlockSize>>>(...);

This is useful for templated or generic kernels where you don't know the exact register usage until compile time. For kernels with a natural shape (like matmul tiles), stick with the hand-computed approach so you keep control of TILE.

Then, for either path, profile with Nsight Compute. The theoretical process above gets you 80% of the way; the profiler shows the remaining 20% (bank conflicts, un-coalesced loads, stall reasons).

12. Summary — The Recipe on One Page

The complete design process
Step 0:  Query cudaGetDeviceProperties, write down 5 limits
         (numSMs, maxTPB, maxTPSM, maxBPSM, sharedPerSM)

Step 1:  threadsPerBlock = TILE × TILE
         - start TILE = 16   (gives 256 threads)
         - must be ≤ maxTPB, must be multiple of 32

Step 2:  sharedPerBlock = 2 × TILE² × bytesPerElement
         - verify TILE² ≤ sharedPerSM / (8 × desiredBlocksPerSM)

Step 3:  blocksPerSM = min of:
            maxBPSM
            maxTPSM / threadsPerBlock
            sharedPerSM / sharedPerBlock
            regsPerSM / (regsPerThread × threadsPerBlock)
         occupancy = blocksPerSM × threadsPerBlock / maxTPSM
         target occupancy ≥ 50%, preferably ≥ 75%

Step 4:  concurrentBlocks = numSMs × blocksPerSM
         if outputTiles >> concurrentBlocks:
             launch 2-4 × concurrentBlocks  (use grid-stride)
         else:
             launch outputTiles blocks directly
Remember:
Hardware picks the budget. You pick the tile. The compiler picks the registers. The runtime picks the schedule.
Your job is to make the four limits balance, so no resource — threads, warps, shared memory, registers — is the bottleneck alone.
