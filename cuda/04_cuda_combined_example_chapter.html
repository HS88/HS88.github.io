1. Why GT200?

Modern GPUs (Hopper, Ampere, Ada) have specs so generous that the grid-stride pattern often looks optional — you can simply launch one block per output tile and the hardware shrugs. On an older GPU like the GT200, the budget is tight enough that the combined pattern isn't a stylistic preference, it's an engineering necessity. Grounding the example on GT200 makes the "why" of every launch choice visible.

GT200 In One Sentence
Released June 2008, the GT200 is the chip at the heart of the GeForce GTX 280 / 285 and the Tesla C1060 / S1070. It has 30 streaming multiprocessors, each hosting 8 CUDA cores, for a total of 240 CUDA cores. Compute capability 1.3.

2.2 What the Limits Mean for a Kernel Launch

Combine the limits and the picture tightens quickly:

  • Maximum concurrent threads on the chip: 30 SMs × 1,024 threads/SM = 30,720 threads. That's the total amount of real parallelism GT200 can field at any instant. A kernel that needs more "work units" than this must, by definition, serialize some work.
  • Ideal threads per block: Multiples of 32 (one warp). Common sweet spots: 128, 256, or 512. For tiled matmul we usually pick 16×16 = 256 (a 16-wide warp alignment that keeps memory coalesced).
  • Blocks per SM for max occupancy: 1,024 ÷ 256 = 4 blocks of 256 threads each. (The 8-blocks-per-SM ceiling kicks in for smaller blocks.)
  • Target concurrent blocks on the chip: 30 SMs × 4 blocks/SM = 120 blocks. This is the rough "sweet spot" launch size for a well-tuned matmul on GT200.
Figure 2.1 — GT200 chip: 30 streaming multiprocessors. Each SM is its own small parallel processor. A kernel launch distributes blocks across these 30 SMs; anything beyond ~120 live blocks has to queue.

2.3 Why Grid-Stride Is Mandatory

Consider a modest matrix multiplication, C = A × B, with N = 4,096 and tile size 16. The number of output tiles is (4,096 / 16)² = 256² = 65,536 output tiles.

If we tried to launch one block per output tile — the "naïve one-block-per-tile" approach — we would need a dim3 grid of 256 × 256 blocks. That fits under the 65,535 limit in each axis but it is deeply wasteful:

  • The GPU has physical room for only ~120 concurrent blocks.
  • The other 65,416 blocks sit queued, waiting for SMs to free up.
  • Each block carries small fixed scheduling overhead. 65,536 blocks of overhead vs. 120 blocks of overhead is three orders of magnitude of waste.

The alternative is to launch the sweet-spot number of blocks (~120) and have each block iterate through multiple output tiles using a grid-stride loop at the block level. Each block does roughly 65,536 ÷ 120 ≈ 546 output tiles during its lifetime. This is the combined pattern. Grid-stride at the block level handles the "too many output tiles" problem; shared-memory tiling inside each tile handles the "redundant global memory reads" problem.

The Combined Pattern on GT200

Launch ~120 blocks of 256 threads. Each block owns a 16 × 16 output tile at a time, and uses a grid-stride loop to advance to its next output tile after finishing the current one. Within each output tile, the 256 threads cooperate to load shared-memory tiles of A and B, step through the K dimension in phases, and accumulate the dot product. Two loops, two patterns, one kernel.

3. The Small Problem We Will Solve

To make every memory movement traceable by hand, we scale the problem down by three orders of magnitude. The pattern is identical to the 4,096 × 4,096 case; the numbers are small enough to pencil out.

3.1 Dimensions and Values

  • Matrix A is M × K = 5 × 4
  • Matrix B is K × N = 4 × 7
  • Matrix C = A × B is M × N = 5 × 7
  • Tile size T = 2

Why this exact shape?

  • M = 5 is not divisible by T = 2 → the bottom row of output tiles is a partial tile (only row 4 is valid; "row 5" is off the end of C).
  • N = 7 is not divisible by T = 2 → the right column of output tiles is also partial (only col 6 is valid).
  • K = 4 IS divisible by T = 2 → the inner "phases" loop is clean (exactly 2 phases), which removes a distraction while we focus on the row/col edges.
  • Non-square, rectangular dimensions force the code to distinguish M, N, K — a common source of bugs.
Figure 3.1 — The concrete inputs we will trace. B is constructed so that every column of B is identical, which makes every column of C identical too. This isn't a limitation of the algorithm; it's a choice that makes hand-verification trivial — we only need to remember one number per row of C.

3.2 The Expected Answer

Because every column of B is identical (col 0 = col 1 = ... = col 6), every column of C is identical too. Row r of C always equals 1·A[r,0] + 2·A[r,1] + 3·A[r,2] + 4·A[r,3]. Plugging in:

Row of AFormulaValue for every column
r=01·1 + 2·2 + 3·3 + 4·4 = 1 + 4 + 9 + 1630
r=15 + 12 + 21 + 3270

So the hardest cell to compute — the corner cell C[4, 6] — equals 190. If our kernel produces that, we know it got the boundary handling right in both dimensions at once.

4. Choosing the Launch Configuration

4.1 Tile Size, Threads per Block, Blocks

For this pedagogical example we pick:

  • Tile size T = 2, so each shared-memory tile is 2 × 2 floats = 16 bytes. Two such tiles (As, Bs) = 32 bytes of shared memory per block — comically small, which is the point.
  • Threads per block = (T, T) = (2, 2) = 4 threads. One thread per element of the output tile.
  • Blocks = (2, 2) = 4 blocks. Deliberately small so that we have fewer blocks than output tiles, forcing the block-level grid-stride loop to do work.

In a real workload on GT200 you would pick T = 16, giving 256 threads per block, and launch ~120 blocks. The math scales directly from what we are about to trace.

4.2 The Resulting Tile Grid

Output matrix C is 5 × 7. With T = 2, the number of row-tiles is ceil(5/2) = 3 and the number of col-tiles is ceil(7/2) = 4. That gives us 3 × 4 = 12 output tiles, some of which are partial because the dimensions aren't divisible by T.

Figure 4.1 — The output matrix C decomposed into 12 tiles. Each colored tile is owned by one of the 4 launched blocks. Because 5 is not a multiple of 2 and 7 is not either, row-tile 2 and col-tile 3 are only partially inside C — the rest is padding.

5. The OUTER Loop: Block-Level Grid-Stride

5.1 Who Owns Which Output Tile

With 4 blocks for 12 tiles, each block must take on multiple tiles. The block-level grid-stride loop assigns them like this: block (bx, by) starts at output tile (by, bx) and then jumps forward by gridDim.y row-tiles and gridDim.x col-tiles respectively, until it runs off the end. 

for (int tileY = blockIdx.y; tileY < rowTiles; tileY += gridDim.y)   // outer-outer
for (int tileX = blockIdx.x; tileX < colTiles; tileX += gridDim.x)   // outer-inner
    computeOneOutputTile(tileY, tileX);

Instantiating for gridDim = (2, 2), rowTiles = 3, colTiles = 4:

Block (bx, by)tileY values visitedtileX values visitedOutput tiles ownedCount
(0, 0)0, 20, 2(0,0), (0,2), (2,0), (2,2)4
(1, 0)0, 21, 3(0,1), (0,3), (2,1), (2,3)4
(0, 1)10, 2(1,0), (1,2)2
(1, 1)11, 3(1,1), (1,3)2

Total: 4 + 4 + 2 + 2 = 12 tiles. Every tile is covered exactly once. Notice how block (0, 1) and block (1, 1) only do 2 tiles each — because there are only 3 row-tiles, the inner loop stops after one iteration for blockIdx.y == 1. This asymmetry doesn't hurt correctness; it just means those two blocks finish a bit earlier.

6. The INNER Loop: Shared-Memory Tiling at a Boundary

Now we zoom in all the way: inside the 4th pass of Block (1, 0), computing the corner output tile (2, 3). The four threads of this block cooperate for two phases, with padding on both the row and column sides, to produce the single valid output C[4, 6] = 190.

6.1 Setting Up Tile (2, 3) — The Corner Case

For this tile:

  • outRow = tileY × TILE = 2 × 2 = 4. Thread (ty, tx) handles output row = outRow + ty, i.e. row 4 or row 5.
  • outCol = tileX × TILE = 3 × 2 = 6. Thread (ty, tx) handles output col = outCol + tx, i.e. col 6 or col 7.
  • Only Thread (0, 0) targets a real output cell (C[4, 6]). The other three threads will do all the work but discard their result.

This is a crucial feature of the pattern: every thread still participates in the cooperative load and compute. They can't just early-exit, because the shared tile needs to be fully populated — every thread's slot in As and Bs contributes to the dot products of other valid threads. The elegant trick is to load zero for out-of-bounds elements. Zero kills the multiply, so the padding contributes nothing to the sums.

Three Guards, Three Different Jobs
  1. Guard on the A load — "is this A-element actually inside A?" If no, store 0 in shared.
  2. Guard on the B load — "is this B-element actually inside B?" If no, store 0 in shared.
  3. Guard on the C write — "is this output actually inside C?" If no, skip the store.

All three are independent. The A guard protects reads, the B guard protects reads, and the C guard protects writes. You need all three.

6.2 Phase 0: Load (with padding) and Partial Multiply

Phase 0 covers K-dimension indices 0 and 1. Each thread (ty, tx) loads one element of A and one of B:

  • A-load address: A[(outRow + ty), (0 + tx)] = A[4+ty, 0+tx]
  • B-load address: B[(0 + ty), (outCol + tx)] = B[0+ty, 6+tx]
Figure 6.1 — Phase 0 of block (1, 0)'s 4th pass. The row-5 slots of A and the col-7 slots of B both get padded with zero. Only thread (0, 0) is doing arithmetic that matters; the other three carry zeros through the multiply-add but will be filtered out by the final write-back guard.

6.3 Phase 1: Load Again and Accumulate

Phase 1 covers K-dimension indices 2 and 3. The shared arrays As and Bs are overwritten with new data:

  • A-load: A[4+ty, 2+tx] — row 4 is valid, row 5 pads to zero.
  • B-load: B[2+ty, 6+tx] — col 6 is valid, col 7 pads to zero.
Figure 6.2 — Phase 1 completes Thread (0, 0)'s dot product: 53 (phase 0) + 137 (phase 1) = 190, matching the expected answer. The three OOB threads produced zero, which the write-back guard then discards.

6.4 Write-Back with Bounds Check

After the last phase, every thread has a sum variable. Only threads whose global (row, col) falls inside the real output matrix C are allowed to write: 

if (row < M && col < N) {
    C[row * N + col] = sum;
}

Why Three Threads Did "Useless" Work
It may feel wasteful that threads (0,1), (1,0), and (1,1) carried zeros through the entire computation only to throw everything away. But those threads were essential: each of them loaded one slot of shared memory. Without them, thread (0, 0) would have been staring at uninitialized values at As[1][*] and Bs[*][1], which the inner for k loop reads unconditionally. The cost of the "wasted" threads is the price of keeping the cooperative load pattern simple and barrier-friendly.

7. The Complete Kernel

Here, in one place, is the full kernel we just hand-traced. Nothing hidden: 

#define TILE 2

__global__ void matMulTiledStrided(
        const float* __restrict__ A,
        const float* __restrict__ B,
        float* __restrict__ C,
        int M, int N, int K)
{
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x;
    int ty = threadIdx.y;

    int rowTiles = (M + TILE - 1) / TILE;   // ceil(M / TILE)
    int colTiles = (N + TILE - 1) / TILE;   // ceil(N / TILE)
    int numPhases = (K + TILE - 1) / TILE;  // ceil(K / TILE)

    // ===== OUTER: block-level grid-stride over the output tile grid =====
    for (int tileY = blockIdx.y; tileY < rowTiles; tileY += gridDim.y) {
      for (int tileX = blockIdx.x; tileX < colTiles; tileX += gridDim.x) {

        int row = tileY * TILE + ty;        // this thread's output row
        int col = tileX * TILE + tx;        // this thread's output col
        float sum = 0.0f;

        // ===== INNER: cooperative shared-memory tiling over K =====
        for (int phase = 0; phase < numPhases; ++phase) {
            int aCol = phase * TILE + tx;
            int bRow = phase * TILE + ty;

            // Guarded cooperative load (pad with zero when out of bounds)
            As[ty][tx] = (row < M && aCol < K) ? A[row * K + aCol] : 0.0f;
            Bs[ty][tx] = (bRow < K && col < N) ? B[bRow * N + col] : 0.0f;

            __syncthreads();                 // tile is fully loaded

            // Multiply-add along the K-dimension inside the tile
            #pragma unroll
            for (int k = 0; k < TILE; ++k) {
                sum += As[ty][k] * Bs[k][tx];
            }

            __syncthreads();                 // safe to overwrite next phase
        }

        // Guarded write-back — only real output cells get stored
        if (row < M && col < N) {
            C[row * N + col] = sum;
        }
      }
    }
}

// --- Host-side launch ---
dim3 threads(TILE, TILE);                    // 2 × 2 = 4 threads per block
dim3 blocks(2, 2);                           // 4 blocks total (toy example)
matMulTiledStrided<<<blocks, threads>>>(dA, dB, dC, /*M=*/5, /*N=*/7, /*K=*/4);

Three nested loops total: two outer grid-stride loops over the output-tile grid, one inner phase loop over K. Three bounds-guards: one on each of the two loads, one on the write. Two __syncthreads() inside the phase loop.

Figure 9.1 — The combined pattern decomposes into two independent axes. The block-level grid-stride loop is "where do I go next after finishing this tile?"; the shared-memory tiling is "how do I compute this one tile efficiently?". Each solves a different problem; together they are complete.
The One Thing to Walk Away With

A production matmul kernel has three loops in the kernel body and three bounds guards:

  • Outer two loops = grid-stride at the block level → every output tile gets owned by exactly one block.
  • Inner loop = tiling phases over the K dimension → each phase loads one shared-memory tile and does TILE multiply-adds.
  • Three guards = one on each shared-memory load (pad with zero), one on the final C store (discard writes to padding).

Once you can write that from memory on an index card, you can scale it from 5×7 on GT200 all the way up to 4096×4096 on an H100 without changing a single structural line — only the tile size, the number of blocks, and perhaps the data type.

If you can look at the trace of C[4, 6] = 190 and see why every zero got where it got, you understand the combined pattern. That same mental movie plays out identically for every tile in a 65,536-tile matmul on modern hardware; the only difference is scale.
