1. The Problem: Global Memory Is a Bottleneck

In the previous chapter we solved the problem of mapping threads to data: no matter how large the dataset, a grid-stride loop lets a fixed number of threads cover everything. But solving that problem only guarantees correctness; it says nothing about speed. Once every element is reached, a new, more subtle question appears:

Central Question
A modern GPU can perform roughly ten trillion floating-point operations per second, but its global memory can only deliver one or two trillion bytes per second. If each arithmetic operation requires its own trip to global memory, the GPU will spend the vast majority of its time waiting. How can we make every fetched byte do more work before it is thrown away?

This is the memory-bandwidth bottleneck, and it is the single most important performance issue in GPU programming. The answer, in a word, is tiling: we partition the data into small blocks that fit into a tiny but extremely fast on-chip memory, we load each block exactly once, and we let many threads reuse it before we move on.

By the end of this chapter, you will understand the tiling pattern well enough to apply it to matrix multiplication, convolutions, stencil computations, and any other kernel where the same data is touched more than once.

2. Prerequisites — The GPU Memory Hierarchy

Before we can talk about tiling, we need to see the landscape of memories that live on a GPU. Each kind of memory has a different size, a different latency, and a different scope of visibility.

2.1 The Four Levels

A CUDA-capable GPU has essentially four layers of memory that a programmer should know about:

  1. Registers — One cycle of latency. Private to a single thread. A few hundred 32-bit registers per thread.
  2. Shared memory (also called L1 scratchpad) — Roughly 20–30 cycles. Shared by all threads within a block. Typically 48 KB to 164 KB per Streaming Multiprocessor (SM).
  3. L2 cache — A few hundred cycles. Shared across all SMs on the chip. A few megabytes in total.
  4. Global memory (the device DRAM) — 400 to 800 cycles. Visible to every thread of every kernel. Several gigabytes, but very far away.
Figure 2.1 — A rough picture of the GPU memory hierarchy. Each level trades size for speed. Global memory is roughly twenty to forty times slower than shared memory.
The 20× Speed Gap
Put the numbers in your head: a single global-memory load can take as long as twenty to forty shared-memory loads. That ratio is the engine that makes tiling worth the trouble. If we can reuse each global load even 10 times out of shared memory, we have effectively made the kernel 10× faster.

2.2 Shared Memory: The Programmer's Cache

Unlike a CPU cache — which is managed automatically by hardware — shared memory is managed by you, the programmer. You decide what to load into it, when, and how it is laid out. You are, in effect, writing your own tiny cache-management routine. That sounds like a burden, but it is actually a gift: it means you can design a loading pattern that is perfect for your specific algorithm.

In CUDA, shared memory is declared inside a kernel with the __shared__ qualifier: 

__global__ void myKernel(float* A) {
    __shared__ float tile[16][16];   // 16 × 16 × 4 B = 1024 B of shared memory
    // ... each block has its own private copy of `tile` ...
}

Every block that is launched receives its own private copy of the shared array. Threads inside the same block see the same shared memory; threads in different blocks do not.

2.3 Threads Talking: __syncthreads()

Because threads inside a block run semi-independently (they are scheduled in groups of 32 called warps, but different warps make progress at different rates), we need a way to say: "Everybody wait here until all of us have arrived." That is the job of the barrier function __syncthreads().

Analogy: The Group Hike

Imagine a team of hikers walking a trail together. Occasionally the trail reaches a river. Some hikers arrive first; some lag behind. Before anyone wades in, the group pauses at the bank until every member has arrived. Only then does the group cross as one.

In a CUDA block, __syncthreads() is that pause at the river. Every thread in the block must reach the barrier before any thread may continue.

Tiling always uses this pattern:

  1. All threads cooperatively load a tile from global memory into shared memory.
  2. __syncthreads() — wait until the tile is fully loaded.
  3. All threads compute using the tile.
  4. __syncthreads() — wait until the computation is done before overwriting the tile with the next one.

3. The Naïve Approach and Its Hidden Cost

To feel the pain that tiling cures, let us look at a kernel that works but wastes memory bandwidth catastrophically. The classical example is matrix multiplication.

3.1 Matrix Multiplication, the Simple Way

To multiply two N × N matrices, C = A × B, each output element C[row][col] is the dot product of one row of A and one column of B: 

C[row][col] = Σk=0..N-1  A[row][k] * B[k][col]

The obvious CUDA kernel assigns one output element to each thread: 

__global__ void matMulNaive(const float* A, const float* B, float* C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    if (row < N && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < N; k++) {
            sum += A[row * N + k] * B[k * N + col];   // two global loads per k
        }
        C[row * N + col] = sum;
    }
}

3.2 Counting Global Memory Reads

This kernel is correct, but let us count how many bytes it reads from global memory.

  • Each thread performs N iterations of its inner loop.
  • Each iteration reads one element of A and one element of B — that is 2N global loads per output element.
  • There are N² output elements, so total global loads = 2N³.

Now compare that to the minimum possible: there are only 2N² unique input elements (A and B together). The naïve kernel therefore re-reads each input element from global memory roughly N times.

Figure 3.1 — In the naïve kernel, each row of A is re-fetched by every output column, and each column of B is re-fetched by every output row. The green cell C[0,1] lies at the crossing of the two highlighted stripes. For N × N matrices, the redundancy factor is N.

For N = 1024, that means 2 billion global loads instead of the ideal 2 million. A thousand-fold increase in memory traffic — most of it duplicated. This is the hidden cost, and tiling is going to make it go away.

4. The Tiling Idea — Load Once, Reuse Many Times

The heart of tiling is a single, simple observation: whenever multiple threads need the same piece of data, that data should be fetched from global memory once, parked in shared memory, and reused by all the threads that need it.

4.1 The "Bring the Books to Your Desk" Analogy

Analogy: Group Study at the Library

You and three classmates have to answer 16 questions. Every question requires looking up a fact in a reference book that lives in the library across campus. The naïve approach: each person, for each of their four questions, walks to the library, reads one line, and walks back. Four people × four questions × one trip = 16 trips to the library.

A smarter approach: the four of you meet at a shared study table. One person goes to the library and borrows the book, bringing it to the table. Now all four of you can read any fact from the book without leaving. You answer all 16 questions from the single book on the table. Total trips: one.

The library is global memory. The shared study table is shared memory. The book is a tile. The borrowing phase is the cooperative load. And the "wait until everyone sits down before starting" moment is __syncthreads().

4.2 What Is a Tile?

A tile is a small, rectangular sub-block of the input data — small enough to fit into shared memory, large enough that many threads can reuse it. In matrix multiplication we usually pick a square tile, for example 16 × 16 floats = 1,024 bytes, and we size our thread block to exactly match: 16 × 16 = 256 threads. Each thread of the block is responsible for loading one element of the tile.

The Tile Contract

Inside a block of T × T threads, we agree on three rules:

  1. Each thread loads exactly one element of the tile from global memory into shared memory.
  2. We __syncthreads(), then everyone is free to read any element of the tile.
  3. After the computation, we __syncthreads() again before reusing the shared buffer.

Because of rule 2, each element — loaded once from the slow DRAM — is read T times from the fast on-chip memory. We have amplified every global load by a factor of T.

5. Tiled Matrix Multiplication — The Walkthrough

Now we are ready to apply tiling to matrix multiplication. We will trace a tiny example by hand so that every memory movement is visible.

5.1 Setup: 4×4 Matrices with 2×2 Tiles

To keep the drawings small, we will multiply two 4 × 4 matrices with a tile size of 2. The grid is 2 × 2 blocks, and each block has 2 × 2 = 4 threads. Each block will compute one 2 × 2 tile of the output C.

  • Matrix size: N = 4
  • Tile size: T = 2
  • Grid: 2 × 2 blocks
  • Block: 2 × 2 threads → 4 threads per block
  • Phases per block: N/T = 2 (we have to slide the tile across the matrix twice to accumulate the full dot product)
N/T = 2 phases: in each phase it loads one A-tile and one B-tile into shared memory, multiplies them, and accumulates the partial result into its own output tile. After 2 phases the dot products are complete.
Figure 5.1 — Each block owns one output tile. To compute it, the block iterates over a strip of A and a strip of B, one tile at a time.

5.2 Phase 0: Load and Partial Multiply

Focus on block (0, 0). In phase 0, the four threads of the block cooperatively load the left-most 2 × 2 tile of A and the top-most 2 × 2 tile of B into two shared arrays, As and Bs:

Figure 5.2 — Phase 0 of tiled matmul. Four threads each load one element of A and one of B into shared memory, barrier, then each thread performs 2 multiply-adds using shared data.

Notice what happened: the four elements of the A-tile (A00, A01, A10, A11) were fetched from global memory exactly once each. Yet after the barrier, every thread in the block can read any of them. In particular, thread (0,0) and thread (0,1) both read As[0,0] and As[0,1] — so each of those global loads has been reused twice already, and we have not yet finished the phase.

5.3 Phase 1: Load Again and Accumulate

After phase 0, each thread holds a partial dot product (the first two of the four terms). To complete the sum, we slide one tile to the right in A and one tile down in B, reload shared memory, barrier, and accumulate the remaining two terms.

Figure 5.3 — Phase 1 reuses the same shared arrays As and Bs to hold the next pair of tiles. Each thread's running sum now accumulates the remaining 2 terms of the 4-term dot product.

After phase 1, each thread's local accumulator sum holds the complete dot product. Writing it to C[row, col] finishes the output tile.

The Accounting

Block (0,0) produced a 2 × 2 output tile (four elements of C). To do so:

  • It fetched 8 global values from A (4 in each of 2 phases).
  • It fetched 8 global values from B.
  • Total: 16 global loads.

The naïve kernel, for the same 4 output elements, would have performed 2 · N = 8 loads per element = 32 global loads. We cut traffic in half with a tile size of only 2. With a tile size of 16 we would cut traffic by 16×.

5.4 Why Two __syncthreads() Calls?

The first barrier — after the load — is obvious: we must not start reading shared memory until every thread has finished writing its element. Without it, a fast thread could read a slot that has not yet been written, and it would get garbage.

The second barrier — at the end of the compute step, before the next phase overwrites shared memory — is less obvious but equally crucial. Suppose we skip it. Thread (0,0) finishes its 2 multiply-adds quickly and jumps to the next iteration of the outer loop. It starts overwriting As and Bs with phase-1 data. Meanwhile, thread (1,1), which was a bit slower, is still reading As[1,1] from phase 0. The result: a race condition and silently wrong answers.

The Two-Barrier Rule
Every tiled kernel has two __syncthreads() inside the outer loop: one after the load (so compute can safely read shared memory), and one after the compute (so the next phase's load can safely overwrite shared memory). Skipping either barrier produces race conditions that sometimes "work" on small inputs and fail mysteriously at scale.

6. The Code Pattern

6.1 The Kernel

Here is the full tiled matrix-multiplication kernel. Study it alongside the walkthrough above; every variable corresponds to something in the diagrams.

#define TILE 16

__global__ void matMulTiled(const float* A, const float* B, float* C, int N) {
    // --- Shared-memory tiles, one copy per block ---
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    // --- Which output element does THIS thread compute? ---
    int row = blockIdx.y * TILE + threadIdx.y;
    int col = blockIdx.x * TILE + threadIdx.x;

    float sum = 0.0f;

    // --- Loop over all the tiles along the K dimension ---
    int numPhases = N / TILE;                   // assume N % TILE == 0 for now
    for (int phase = 0; phase < numPhases; ++phase) {

        // (1) COOPERATIVE LOAD: each thread loads ONE element
        As[threadIdx.y][threadIdx.x] = A[row * N + (phase * TILE + threadIdx.x)];
        Bs[threadIdx.y][threadIdx.x] = B[(phase * TILE + threadIdx.y) * N + col];

        // (2) Wait for the whole tile to be loaded
        __syncthreads();

        // (3) COMPUTE: use shared-memory values TILE times
        for (int k = 0; k < TILE; ++k) {
            sum += As[threadIdx.y][k] * Bs[k][threadIdx.x];
        }

        // (4) Wait before overwriting shared memory with the next tile
        __syncthreads();
    }

    // --- Write the completed dot product ---
    C[row * N + col] = sum;
}

6.2 Host-Side Launch

dim3 threads(TILE, TILE);                    // 16 × 16 = 256 threads per block
dim3 blocks(N / TILE, N / TILE);             // one block per output tile
matMulTiled<<<blocks, threads>>>(d_A, d_B, d_C, N);

7. The Math — Why Tiling Wins

We can now quantify the benefit. Let N be the matrix dimension and T the tile size.

7.1 Global Reads: Naïve vs Tiled

In the naïve kernel, each of the N² output threads reads N elements of A and N elements of B. Total global loads: 2 N³.

In the tiled kernel, each block loads N/T A-tiles and N/T B-tiles, and each tile contains T² elements. There are (N/T)² blocks. So the total global loads are: 

(N/T)² blocks × (N/T) phases × 2 tiles × T² elements per tile
= (N²/T²) × (N/T) × 2 × T²
= 2 N³ / T

In other words, tiling divides global memory traffic by exactly the tile size T.

7.2 Arithmetic Intensity

Arithmetic Intensity

Arithmetic intensity = (useful arithmetic operations) ÷ (bytes transferred from global memory). Higher is better: a kernel with low intensity will be memory-bound, meaning the compute units sit idle waiting for data. A kernel with high intensity is compute-bound, meaning the GPU's FLOPs are the bottleneck — which is almost always what you want.

Matrix multiplication does 2 N³ floating-point operations (one multiply and one add per k). Each float is 4 bytes.

  • Naïve: 2 N³ FLOPs ÷ (2 N³ × 4 bytes) = 0.25 FLOP/byte — deeply memory-bound.
  • Tiled with T = 16: 2 N³ FLOPs ÷ (2 N³ / 16 × 4 bytes) = 4 FLOP/byte — approaching the sweet spot of modern GPUs.
  • Tiled with T = 32: 8 FLOP/byte — comfortably compute-bound on many devices.

In other words, tiling is not just a 10× or 20× optimization. It changes what the bottleneck is, moving the kernel from the slow memory lane into the fast compute lane.

8. Handling Boundaries

So far we assumed the matrix dimension is divisible by the tile size. In real life, N might be 1,000 and T might be 16 — and 1,000 is not divisible by 16. Two things can go wrong:

  1. An out-of-bounds thread tries to load A[row, k] where either row or k is ≥ N — a read past the end of the array.
  2. An out-of-bounds thread tries to write C[row, col] where either index is ≥ N — a write past the end.

The standard fix is to load a padded tile: whenever a thread's global index is out of range, it writes a zero into its shared slot. Zeros are the identity for addition and the annihilator for multiplication, so they contribute nothing to the sum. 

// Guarded cooperative load
int aCol = phase * TILE + threadIdx.x;
int bRow = phase * TILE + threadIdx.y;

As[threadIdx.y][threadIdx.x] = (row < N && aCol < N)
                               ? A[row * N + aCol] : 0.0f;
Bs[threadIdx.y][threadIdx.x] = (bRow < N && col < N)
                               ? B[bRow * N + col] : 0.0f;

__syncthreads();

for (int k = 0; k < TILE; ++k) {
    sum += As[threadIdx.y][k] * Bs[k][threadIdx.x];
}
__syncthreads();

// Guarded store
if (row < N && col < N) {
    C[row * N + col] = sum;
}

// Host-side: round grid UP to cover N
dim3 blocks( (N + TILE - 1) / TILE, (N + TILE - 1) / TILE );
Figure 8.1 — When the matrix dimension is not a multiple of the tile size, threads whose global index is out of range write 0 into their shared slot. The arithmetic still produces the correct dot product.

9. Common Pitfalls and Debugging Tips

9.1 Pitfall: Missing __syncthreads()

The most common tiling bug. Symptoms: the kernel produces correct results for small matrices but wrong results — often non-deterministic — for larger ones. Rule of thumb: for every shared-memory load there is a __syncthreads(); for every end-of-phase there is a __syncthreads().

9.2 Pitfall: __syncthreads() Inside a Conditional

if (row < N) {
    // ...
    __syncthreads();   // DANGER: some threads may skip the barrier!
}

If any thread in the block skips the barrier, __syncthreads() hangs the entire block forever. The barrier must be reached by every thread. Always place __syncthreads() in unconditional code.

9.3 Pitfall: Shared-Memory Size Overflow

A tile of 32 × 32 floats is 4 KB — fine. Two such tiles are 8 KB — also fine. But 64 × 64 would be 16 KB per tile, 32 KB for both, and you may begin to hit per-SM limits that shrink occupancy (the number of blocks that can be resident per SM). A good rule: keep total shared memory per block at or below 8 KB unless you are willing to measure the trade-off.

9.4 Pitfall: Bank Conflicts

Shared memory is organized into 32 banks, each 4 bytes wide. If two threads of the same warp access different addresses in the same bank, the accesses are serialized, costing you performance. For a float As[TILE][TILE], accessing As[k][tx] for tx = 0…31 is conflict-free when TILE is 32 (one access per bank), but accessing As[ty][k] for ty = 0…31 when TILE = 32 maps all 32 threads to the same bank — a 32-way conflict. A classic cure is to pad: declare __shared__ float As[TILE][TILE + 1]. The extra column shifts the row stride and restores conflict-free access.

9.5 Pitfall: Writing to the Wrong Index of the Shared Array

It is tempting to write As[row][col] instead of As[threadIdx.y][threadIdx.x]. The shared array is indexed by the thread's position within the block, not by the global row/column. Each block has its own private shared memory that starts over at [0][0].

9.6 Debugging Technique: Serial Launch

Just like with grid-stride loops, you can launch the tiled kernel with a single block of a single thread for debugging: 

matMulTiled<<<1, dim3(TILE,TILE)>>>(d_A, d_B, d_C, TILE);  // single block

Pick N = TILE so there is exactly one phase. Add printf() calls inside the kernel to dump each thread's As and Bs values after the barrier. Cross-check against a hand calculation.

10. Beyond Matrix Multiplication — Other Tiled Kernels

Matrix multiplication is the clearest demonstration of tiling, but the same pattern appears in many kernels. Any time a computation has data reuse — the same input element contributes to many outputs — tiling is a candidate. Here are the usual suspects:

  • 2D convolution (stencils, blur, sharpen, etc.) — A convolution with a 5 × 5 kernel touches 25 input pixels for every output pixel. Adjacent output pixels share most of those inputs. A tile loads a block of the input image plus a halo (a border of neighboring pixels), lets every thread convolve against shared memory, and dramatically cuts global reads.
  • Reduction (sum, max, mean) — While the "classic" reduction uses shared memory as a tree-shaped accumulator, the fundamental trick is the same: pull a chunk of data into shared memory once, then let the threads of the block cooperate using that chunk.
  • Transpose — Naïve transpose has uncoalesced writes; a tiled transpose loads a 32 × 32 tile into shared memory with coalesced reads, then writes it out with coalesced writes.
  • Deep-learning attention and softmax — The state-of-the-art "FlashAttention" kernel is, at its core, an elaborate tiling scheme for the K and V matrices of a transformer. The same idea scaled to a research paper.
The Underlying Pattern
Whenever you find yourself thinking "many threads need to look at the same data", reach for a tile. Load the data once from global memory, barrier, let everyone read it, barrier, move on to the next tile. This single idiom powers most of the fast kernels you will ever write.

12. Summary

Tiling is the pattern that moves a CUDA kernel from the slow lane of global memory into the fast lane of on-chip SRAM. It rests on a handful of ideas that, together, are enough to write fast kernels for most data-parallel problems:

  1. The Problem: Global memory is 20–40× slower than shared memory. A naïve kernel re-fetches the same data over and over, wasting the GPU's bandwidth.
  2. The Solution: Partition the input into tiles that fit in shared memory. Each block cooperatively loads one tile, barriers, computes using shared memory, barriers again, then moves to the next tile.
  3. The Formula: Tiling with tile size T divides global memory traffic by exactly T. Arithmetic intensity scales from 0.25 FLOP/byte (naïve) to T FLOP/byte (tiled).
  4. The Two Barriers: One after the load (so compute can read safely), one after the compute (so the next load can overwrite safely).
  5. The Boundary Fix: When dimensions are not multiples of the tile, pad shared memory with zeros and guard the final write.
  6. Beyond matmul: The same pattern powers convolutions, stencils, reductions, transposes, attention — any kernel with data reuse.
The One Idea to Remember

Load once from global, barrier, reuse many times from shared, barrier, repeat.

If you internalize that single sentence, tiling — and most of the high-performance CUDA that builds on it — is yours.

With grid-stride loops you learned how to make a kernel correct for any input size. With tiling you have now learned how to make the same kernel fast. Together they are the two patterns that will carry you through the first several years of a GPU-programming career.
