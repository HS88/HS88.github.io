CUDA Foundations: A Beginner's Mental Model

"Before you can learn the fancy tricks, you need to know what the pieces are and where they live. This primer is for anyone who has read a CUDA kernel and thought: wait, how does that even work?"
— Why this document exists

This primer answers three questions that trip up almost every CUDA beginner:

  1. When a kernel runs, who can see what? Which variables are private to one thread, which are shared, which are visible everywhere?
  2. When we say "the threads cooperate," what is physically happening? How can one thread get data that another thread wrote?
  3. How does the GPU actually schedule all those thousands of threads? Does it "context switch" like an operating system?

Once these three questions click, everything in the other chapters — grid-stride loops, shared-memory tiling, cooperative loads, boundary padding — becomes obvious. Read this primer first, then go back to the other chapters.

1. The Three Scales: Grid, Block, Thread

A CUDA kernel launch creates a huge collection of lightweight "workers." To keep them organized, CUDA arranges them in a three-level hierarchy. From smallest to largest:

  1. Thread — a single worker. It runs the kernel code once, start to finish. It has its own small set of private variables (registers) and its own unique ID.
  2. Block — a group of threads (up to 1,024 of them) that run together on the same hardware unit (an "SM"). Threads in the same block can cooperate: they can share a small, fast scratchpad and they can wait for each other at barriers.
  3. Grid — the entire collection of blocks that one kernel launch creates. There can be millions of blocks in a grid. Blocks in the same grid cannot talk to each other during the kernel.
Analogy: A Big Office Building
Think of the whole kernel launch as an office building (grid). The building has many meeting rooms (blocks). Each meeting room contains a few employees (threads). Employees in the same room can talk to each other, write on the room's whiteboard, and agree to pause together. Employees in different rooms cannot hear each other, cannot see each other's whiteboards, and cannot coordinate in real time. The only way for one room to send a message to another room is to write it down on the shared company intranet — slow, visible to everyone, no privacy.
Figure 1.1 — Three meeting rooms (blocks) in the same office building (grid). Each room has four employees (threads) and its own private whiteboard. The three whiteboards are completely separate pieces of physical material.

2. What Each Thread Owns For Itself

Every thread has its own registers. A register is the fastest memory on the chip — one cycle of latency — and it is completely private. When you write code like: 

int i = blockIdx.x * blockDim.x + threadIdx.x;
float sum = 0.0f;

…the variables i and sum live in registers. Every thread gets its own copy. If 1,024 threads run this code, there are 1,024 completely separate sum variables on the chip at the same time.

Why This Matters
Think about what this means for the tiled matmul kernel. Each thread had its own float sum accumulator. All four threads in the block were updating their own sum independently; none of them was writing to any other thread's sum. That's why no barriers or locks were needed for the accumulator.

3. What Threads in the Same Block Share

Inside the kernel, when you write: 

__shared__ float tile[16][16];

you are declaring shared memory. Three things to know about it:

  1. The GPU allocates one copy of this array per block. So if 100 blocks are running, there are 100 separate tile arrays — each block sees only its own.
  2. Within a block, every thread sees the same tile. If thread A writes tile[5][7] = 42.0f, then (after a barrier) thread B can read tile[5][7] and get 42.0f.
  3. Shared memory is fast — roughly 20× faster than global memory, because it lives physically close to the SM's compute units.

Shared memory is the GPU's answer to the question "how can threads cooperate?". Its entire purpose is to give every thread in the block access to the same values. It is a shared scratchpad, not a private one.

4. What Everybody Shares (Global Memory)

Then there is global memory — the big DRAM chips soldered to the circuit board. Several gigabytes in size, visible to every thread of every block in every kernel launch. This is where you put your input arrays and read back your output arrays. It persists across kernel launches, too, which is how one kernel's output becomes the next kernel's input.

The trade-off: global memory is slow. 20× to 40× slower than shared memory. This is exactly the bottleneck that the tiling chapter addressed.

5. The Visibility Table — Who Can See What

Here is the most important table in this primer. Memorize this and half of CUDA becomes obvious.

Thing Lives in Visible to Lifetime Speed
int x; inside kernel Register Just this one thread Until the thread finishes Fastest (1 cycle)
__shared__ float t[16]; Shared memory Every thread in this one block Until the block finishes Fast (~20 cycles)
float* A (kernel arg) Global memory (pointed to) Every thread in every block Until the host frees it Slow (~500 cycles)
Kernel arguments like int M Register (copied in at launch) Every thread (same value) Until the thread finishes Fastest
threadIdx.x, blockIdx.x Built-in (per-thread) Just this one thread (each thread sees its own) For the duration of the kernel Fastest
One Simple Rule

The scope of a variable in a CUDA kernel is determined entirely by where you declare it:

  • Declared with just float x; → private to one thread (register).
  • Declared with __shared__ float x; → shared by all threads in one block.
  • Allocated by the host with cudaMalloc → in global memory, visible everywhere.

6. How Threads "Talk" — The Whiteboard Mechanism

This is the question that probably confused you: "How can thread A inside one block get data that thread B produced, while A is computing its dot product?"

The crucial thing to understand is that thread A never reaches into thread B. Threads do not have access to each other's registers. They do not call each other. They do not pass messages directly.

What they do is use a common piece of memory that both of them can see. That memory is shared memory. The pattern always looks like this:

Figure 6.1 — The three-step pattern. In step 1, each thread writes its own value to its own slot — no thread is reading anything from anyone else. In step 2, everyone waits. In step 3, any thread may read any slot. Thread 0 reading s[2] isn't "reaching into" Thread 2 — it's just looking at a slot in a common memory region that happens to have been written by Thread 2.
The Correct Way to Say It

Instead of saying "thread A gets data from thread B", say:

"Thread A reads a shared-memory slot that happens to have been written by thread B."

Both threads are reading and writing the same chunk of memory. Neither thread is touching the other. The shared memory is the medium. The __syncthreads() call is the handshake that makes the writes visible before any read begins.

7. Why Threads in Different Blocks Can't Talk

Each block runs on one SM. Each SM has its own shared-memory hardware — a few tens of kilobytes of SRAM physically wired into the SM. When you declare __shared__ float t[16], the compiler allocates space in the shared-memory hardware of whichever SM the block happens to land on. A block running on SM #3 and a block running on SM #17 are using physically different pieces of silicon for their shared memory. There is simply no wire connecting them.

Similarly, __syncthreads() is a barrier wired into the SM; it can only coordinate threads that are co-located on that SM in that block. There is no cross-SM barrier.

The One Exception: Global Memory
If you really need two blocks to share data, you can have one block write to a global memory location and (in a later kernel launch) a second block read from the same location. But this requires crossing the slow DRAM, and you usually need a separate kernel launch to get a correct ordering. The lesson: design your blocks to be independent whenever possible.

8. Warps — How the GPU Really Runs 32 Threads at a Time

Now let us get to how threads actually execute. This is where the GPU differs most from a CPU.

The hardware does not schedule one thread at a time. It schedules warps. A warp is a group of exactly 32 consecutive threads from the same block. The hardware takes threads 0–31 of your block and bundles them as warp 0; threads 32–63 become warp 1; and so on. If your block has 256 threads, the hardware sees it as 8 warps.

All 32 threads of a warp execute the same instruction at the same time, each on their own data. This is called SIMT (Single Instruction, Multiple Threads). You can think of a warp as a vector unit: one instruction, 32-wide.

Figure 8.1 — Thirty-two threads form one warp. They move together, instruction by instruction, each on their own data.

This has two consequences that bite beginners:

  1. Make your block sizes multiples of 32. If you launch a block of 100 threads, the hardware still bundles them into 4 warps of 32 — but the 4th warp only has 28 "real" threads; the other 4 are wasted. Block sizes of 128, 256, or 512 are classic sweet spots.
  2. If threads in a warp take different branches of an if, they run them serially. This is called "warp divergence." Not catastrophic, but keep if-statements light inside the inner loop of a hot kernel.

9. "Context Switching" — It's Not What You Think

Here's the question you asked: "When one warp is waiting, does the GPU context switch to another warp like an OS?"

The short answer is: yes, the warp scheduler picks a different warp when one is stalled — but no state ever gets saved or loaded. Nothing like an OS context switch happens. Here is why.

Each SM has enough physical register space to hold the complete state of many warps at once — typically up to 32 or 48 resident warps on older architectures, 64 on modern ones. When the kernel launches, the SM parcels out its register file: warp 0 gets its slice, warp 1 gets its slice, and so on, up to however many fit. Those register slices then stay put until each warp finishes.

In each cycle, the SM's hardware scheduler looks at all resident warps and asks: "which warps have an instruction ready to issue right now?" (A warp whose last instruction was a memory load might still be waiting for the data to arrive.) Of the ready warps, the scheduler picks one and runs its next instruction. On the next cycle it might pick a different warp.

Figure 9.1 — Warp scheduling. The scheduler sees all resident warps, picks a ready one each cycle, and issues one of its instructions. The stalled warps don't go anywhere — they just don't get picked that cycle. This is nothing like an OS context switch.
Myth
"When the GPU runs out of threads to run, it pauses one warp and starts another, like a CPU switching between processes."
Truth
No warp is ever paused or resumed in the CPU-process sense. All resident warps live on the SM at the same time with all their registers intact. The scheduler just picks a different ready warp when the current one stalls. There is no state to save, so the switch is free — this is why it is called zero-overhead warp scheduling, and it is one of the GPU's architectural superpowers.
Why "Oversubscribe"?

This scheduling model is also the reason CUDA kernels work best when you launch many more warps than there are execution units. The hardware can only run a handful of warps per cycle, but having 48 warps resident per SM means that at any moment, several of them are likely to be ready. The waiting ones hide the latency of the active ones. This is called latency hiding through oversubscription, and it is why "just launch lots of threads" is good GPU advice.

10. A Tiny Cooperative Example You Can Trace in 30 Seconds

Let's put the whole mental model to work with the smallest possible cooperative kernel: a 4-thread block sums the array [10, 20, 30, 40] to produce 100. Each thread handles one element. 

__global__ void sumFour(const float* input, float* output) {
    __shared__ float s[4];            // one array of 4 floats, shared by all 4 threads
    int tid = threadIdx.x;            // 0, 1, 2, or 3 — unique per thread

    // STEP 1: each thread writes ONE value into its OWN slot of shared memory
    s[tid] = input[tid];

    // STEP 2: barrier — wait for all 4 writes to complete
    __syncthreads();

    // STEP 3: thread 0 reads ALL FOUR slots and sums them
    if (tid == 0) {
        float sum = s[0] + s[1] + s[2] + s[3];   // reads slots other threads wrote!
        output[0] = sum;
    }
}

Now trace it line by line, being careful about who writes what and who reads what:

InstantThread 0Thread 1Thread 2Thread 3Shared array s
Start tid=0tid=1tid=2tid=3 [?, ?, ?, ?]
After write writes s[0]=10 writes s[1]=20 writes s[2]=30 writes s[3]=40 [10, 20, 30, 40]
__syncthreads() all four threads wait here until every write is done [10, 20, 30, 40]
After read reads s[0], s[1], s[2], s[3], sums to 100, writes output (does nothing) (does nothing) (does nothing) [10, 20, 30, 40]

Now look carefully at the "After read" row. Thread 0 read the values 20, 30, and 40 — values written by Threads 1, 2, and 3. That's what people mean when they say "threads cooperate" or "Thread 0 used the other threads' data."

But notice: thread 0 did not contact thread 1. It did not peek at thread 1's registers. It did not send a message. All it did was read s[1] — a slot in the shared array that happened to have been written by thread 1 in the previous step. The shared array is the only medium. The barrier is the only synchronization.

If You Understand This 4-Thread Example, You Understand Tiling

The tiled matmul kernel is exactly the same pattern, scaled up:

  • In tiling, 4 threads cooperatively write 4 values into a shared tile (As). Each writes its own slot.
  • __syncthreads().
  • Then each thread reads multiple slots — including slots written by other threads — to compute its own dot product.

The only new thing in tiling is that the "cooperation" happens in a loop over many phases. The fundamental mechanism — write own slot → barrier → read any slot — is identical.

11. Common Misconceptions, Cleared Up

Misconception 1
"Thread A reaches out to Thread B and pulls data from Thread B's local variables."
Truth
Threads cannot see each other's registers, ever. All inter-thread communication within a block happens through shared memory (or, on newer GPUs, through warp-level intrinsics like __shfl_sync). The sender thread writes a slot; the receiver thread reads that slot. They are communicating through a shared mailbox, not point-to-point.
Misconception 2
"Blocks run one at a time, so block 0 can set up data for block 1."
Truth
Blocks run in an undefined order. Block 17 might run before block 0, and both might be running simultaneously on different SMs. You cannot rely on any ordering. If two blocks need to communicate, you must use global memory and separate kernel launches.
Misconception 3
"When the GPU runs out of execution units, it has to pause one warp and resume it later, saving all its state."
Truth
All resident warps on an SM have their complete register state alive on the SM simultaneously. Switching between them costs nothing. Warps that aren't ready (because they are waiting on memory or at a barrier) simply don't get picked. Warps that are ready get an instruction issued. Zero state moves.
Misconception 4
"A single thread can be split across cores to run faster."
Truth
A thread is the atomic unit of execution. It runs as part of its warp, which runs on a single SM. Threads don't move or split. If you want more parallelism, you launch more threads — not faster threads.
Misconception 5
"I should put as many values as possible into shared memory because it's fast."
Truth
Shared memory is a limited resource (48 KB to ~164 KB per SM, depending on the architecture). If a block uses too much of it, fewer blocks can run concurrently on an SM, hurting occupancy. Use shared memory only for data that is actually reused across threads.
Misconception 6
"__syncthreads() syncs all the threads in the kernel."
Truth
__syncthreads() only syncs threads within one block. There is no built-in intra-kernel barrier across all blocks. If you need every thread in the grid to finish before the next step starts, split your work into two kernel launches — the implicit boundary between kernels is the global barrier.

12. Now You're Ready

Here is the mental model you now have:

  1. A kernel launch creates a grid of blocks of threads. There are millions of threads potentially.
  2. Each thread has its own registers (the private stuff). It has a unique ID so it knows what data to work on.
  3. Threads in the same block can cooperate: they share a small, fast __shared__ scratchpad, and they can synchronize with __syncthreads().
  4. Threads in different blocks cannot talk directly. They each have their own private shared memory. For cross-block coordination you must use global memory and typically separate kernel launches.
  5. When a thread wants data "from" another thread in its block, what really happens is: the other thread wrote a value into shared memory, there was a barrier, and now this thread reads that same shared memory slot.
  6. The hardware groups threads into warps of 32. It schedules warps, not individual threads.
  7. Many warps are resident on the same SM at once, with their full register state intact. When one warp stalls, the scheduler picks another ready warp — this is zero-overhead warp scheduling, not an OS context switch.
The Single Sentence to Remember

Threads never touch each other. They touch the same memory.

If you keep that one sentence in mind, almost every surprising behavior in CUDA becomes predictable.
